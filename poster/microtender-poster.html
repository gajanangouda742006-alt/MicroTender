1. Abstract

MicroTender is a smart civic-maintenance platform where citizens report public issues, administrators review and approve them, and local vendors submit bids to resolve them. The system integrates complaint registration, tender generation, vendor assignment, progress tracking, notifications, anti-fraud checks, and citizen ratings in one normalized relational database application.

2. Problem Statement
  • Manual civic complaint handling is slow and difficult to monitor.
  • There is limited transparency between citizen, authority, and vendor.
  • Bidding, assignment, and work verification are often fragmented.
  • A DBMS-backed workflow is needed for traceability, integrity, and analytics.
3. Objectives
  • Design a normalized database for complaints, tenders, vendors, bids, and ratings.
  • Automate complaint-to-tender conversion with structured workflow states.
  • Track work updates, notifications, and completion verification in real time.
  • Provide secure, role-based access for citizen, vendor, and admin users.

6. Workflow Lifecycle
Citizen submits complaint
System stores complaint + provisional tender
Admin reviews and approves tender
Nearby vendors view and bid
Admin assigns selected vendor
Vendor posts progress updates
Admin verifies completion
Citizen rates completed work
7. ER Diagram and Database Design

Core Entities

Users, Complaints, Micro_Tenders, Vendors, Applications, Work_Updates, Ratings, Notifications, and Fraud_Logs form the main schema.

Relationship Logic

A user files complaints, complaints generate tenders, vendors submit applications, tenders receive work updates, and verified work later receives ratings and notifications.

8. DBMS Highlights
  • Primary keys for every core entity
  • Foreign-key relationships with referential integrity
  • Unique constraints for email and rating duplication control
  • Status-driven lifecycle backed by relational tables
  • Indexes on complaints, tenders, vendors, and notifications
9. Normalization
  • 1NF: Atomic attributes for users, complaints, bids, and ratings
  • 2NF: Non-key data depends on full primary keys
  • 3NF: Repeated business facts are separated into linked tables
  • The schema reduces redundancy and supports scalable query design
